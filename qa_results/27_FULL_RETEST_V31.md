### Поведение при ошибке

1. Пользователь загружает резюме → ✅ успешно
2. Заполняет вакансию → ✅ успешно
3. Выбирает провайдер и модель → ✅ выбор работает
4. Нажимает "Начать оптимизацию" → прогресс-бар запускается
5. Этапы 1-2 показывают ✅ (загрузка, анализ) → **ЛОЖНЫЙ ПРОГРЕСС**
6. На этапе AI оптимизации → ❌ "API-ключ для [провайдер] не настроен"
7. Счётчик остаётся 0/5 (оптимизация не засчитана — корректно)

### Улучшение по сравнению с V29

**Положительный момент:** Сообщение об ошибке теперь **user-friendly**:
- V29: raw technical error → "Error code: 400 - {'error': ...}"
- V31: понятное сообщение → "API-ключ для OpenAI не настроен" + кнопка "Настроить ключи"

### Гипотеза о причине

Баг KEY-CHECK-001 был исправлен для аккаунта test_qa_v30@example.com (09.03.2026), но регрессия проявляется на аккаунте test_qa_v31@example.com (10.03.2026). Возможные причины:

1. **Фикс был привязан к конкретному аккаунту** — возможно, ключи были вручную синхронизированы для test_qa_v30, а не исправлена корневая причина
2. **Race condition при сохранении ключей** — ключи сохраняются в одну таблицу (settings), но читаются optimization engine из другого контекста
3. **Кэширование на стороне сервера** — optimization engine кэширует user context при первом запуске и не перечитывает ключи
4. **Миграция БД / schema mismatch** — структура хранения ключей могла измениться между версиями

## ⚠️ GIGACHAT-AUTH-001 — Новый баг: GigaChat Authorization Error (НОВЫЙ)

**Приоритет: P3 LOW (provider-side, но требует user-friendly обработки)**

### Описание

При попытке оптимизации через GigaChat Pro, вместо ошибки "API-ключ не настроен" (как у OpenAI/Anthropic), GigaChat возвращает ошибку авторизации:

```
Ошибка: LLM-провайдер gigachat-pro: (URL('https://ngw.devices.sberbank.ru:9443/api/v2/oauth'),
400, b'{"error_description":"Can\'t decode Authorization header","error":"invalid_client"}')
```

### Анализ

Это отличается от GIGACHAT-001 (402 Payment Required) из V29/V30. Новая ошибка 400 "Can't decode Authorization header" указывает на:
1. Неверный формат ключа при передаче в Authorization header
2. Ключ возможно передаётся, но в неправильной кодировке (Base64 vs raw)
3. Или ключ НЕ передаётся (KEY-CHECK-001), и сервер получает пустой Authorization header

### Важно

Ошибка отображается как **raw technical data** (URL, HTTP код, тело ответа) — это нарушение UX. Должно быть user-friendly сообщение.

**Компонент:** Frontend → History page / Processing error page

### Описание

Ошибки LLM-провайдеров отображаются как raw technical data на странице истории и на странице обработки ошибок. Включает URL-адреса API, HTTP-коды, тела ответов в JSON/bytes формате.

**GigaChat (V31):**
```

400, b'{"error_description":"Can\'t decode Authorization header","error":"invalid_client"}')
```

**OpenAI o4-mini (из истории V29):**
```
Ошибка: LLM-провайдер openai: Error code: 400 - {'error': {'message':
"Unsupported parameter: 'max_tokens' is not supported with this model.
Use 'max_completion_tokens' instead."
```

User-friendly сообщения:
- GigaChat: "Ошибка авторизации GigaChat — проверьте корректность API-ключа в настройках"
