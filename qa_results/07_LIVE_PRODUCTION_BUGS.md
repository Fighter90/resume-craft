## LIVE-001: Модальное окно вакансии не закрывается по кнопке X и Escape

**Severity:** 🟡 MEDIUM
**Страница:** `/app/vacancy` → кнопка "Подробнее" у вакансии
**Категория:** UI / Accessibility

### Шаги воспроизведения
1. Перейти на `/app/vacancy`
2. Выполнить поиск (например, "Product Manager", "Москва")
3. Нажать "Подробнее" на любой вакансии из списка
4. Модальное окно с деталями вакансии открывается
5. Нажать кнопку X (крестик) в правом верхнем углу модального окна

### Фактический результат
- Клик по кнопке X **не закрывает** модальное окно
- Нажатие клавиши **Escape** также не закрывает модальное окно
- Модальное окно закрывается **только** по клику на overlay (затемнённую область за пределами модального окна)

### Ожидаемый результат
- Кнопка X закрывает модальное окно
- Escape закрывает модальное окно
- Клик на overlay закрывает модальное окно

### Влияние
- Нарушение стандартных паттернов UI
- Проблема доступности (accessibility): клавиатурная навигация не работает
- Пользователь может не догадаться кликнуть на overlay

## LIVE-002: Все LLM-провайдеры недоступны — ошибка "LLM-провайдер all"

**Severity:** 🔴 CRITICAL
**Страница:** `/app/processing`
**Категория:** Функциональность / Backend

### Шаги воспроизведения
1. Загрузить резюме (текст, PDF или DOCX)
2. Выбрать вакансию
3. Выбрать любую AI-модель (GigaChat Pro, OpenAI, и т.д.)
4. Нажать "Начать оптимизацию"

### Фактический результат
- Прогресс остаётся на 0%
- Через ~10 секунд появляется ошибка: **"Ни один LLM-провайдер не настроен. Перейдите в настройки AI и добавьте API-ключ хотя бы для одного провайдера"**
- В истории записи отображаются как: **"Ошибка: LLM-провайдер all временно недоступен"**

### Ожидаемый результат
- Хотя бы один провайдер (GigaChat Pro, обозначенный как "Рекомендуемый" и бесплатный) должен работать
- Если провайдер недоступен, пользователь должен узнать об этом **до** прохождения всего wizard-а

### Влияние
- **Основная функция сервиса полностью неработоспособна** в production
- Пользователь проходит 4 шага wizard-а (загрузка → вакансия → модель → обработка) впустую
- Подрывает доверие к сервису

## LIVE-003: Неудачные оптимизации считаются в лимит тарифного плана

**Severity:** 🟠 HIGH
**Страница:** `/app/settings/subscription`, `/app/dashboard`, sidebar
**Категория:** Бизнес-логика

### Шаги воспроизведения
1. Выполнить оптимизацию, которая завершается ошибкой (LIVE-002)
2. Повторить для другой модели
3. Перейти в Настройки → Подписка

### Фактический результат
- Счётчик показывает **"Использовано 2 из 5 оптимизаций в этом месяце"**
- Sidebar показывает **"2 / 5 оптимизаций"**
- Dashboard показывает **"Оптимизаций: 2"**
- При этом **обе** оптимизации завершились с ошибкой и не дали результата

### Ожидаемый результат
- Неудачные оптимизации (status = failed) **не должны учитываться** в лимите тарифного плана
- Или счётчик должен различать "попыток" и "успешных оптимизаций"

### Влияние
- Пользователь на бесплатном плане (5 оптимизаций/мес) теряет свои попытки из-за серверных ошибок
- Финансовый ущерб пользователю: может быть вынужден перейти на платный план из-за багов сервера

**Категория:** UX / Misleading UI

## LIVE-008: Wizard не проверяет доступность моделей до начала обработки

**Severity:** 🟠 HIGH
**Страница:** Wizard flow (`/app/upload` → `/app/vacancy` → `/app/models` → `/app/processing`)
**Категория:** UX / Architecture

### Шаги воспроизведения
1. Начать новую оптимизацию
2. Загрузить резюме (шаг 1)
3. Выбрать вакансию (шаг 2)
4. Выбрать модель (шаг 3)
5. Запустить обработку (шаг 4)

### Фактический результат
- Пользователь проходит 4 шага wizard-а (3–5 минут)
- Только на последнем шаге (Processing) обнаруживает, что модель не работает
- Нет возможности вернуться к предыдущим шагам без потери прогресса (кроме кнопки "Назад" в браузере)

### Ожидаемый результат
- На шаге выбора модели (ModelSelection) должна быть **проверка доступности** выбранного провайдера
- Если провайдер недоступен — показать предупреждение **сразу**, а не после ожидания
- Кнопка "Начать оптимизацию" должна быть задизейблена для недоступных моделей

### Влияние
- Крайне негативный пользовательский опыт
- Пользователь тратит время на заполнение wizard-а впустую

## LIVE-012: Нет rate limiting на API (подтверждено)

**Severity:** 🟠 HIGH (подтверждено из статического анализа SEC-005 / ARCH-010)
**URL:** `https://resumecraft.ru/api/v1/auth/login`
**Категория:** Безопасность

### Шаги воспроизведения
1. Отправить 10+ POST-запросов на `/api/v1/auth/login` с неправильным паролем
2. Проверить получение ответа на каждый запрос

### Фактический результат
- Все 10+ запросов обработаны, нет блокировки
- Ответ 401 с сообщением "Неверный email или пароль" каждый раз
- Нет captcha, задержки или временной блокировки

### Ожидаемый результат
- Ограничение: максимум 5 попыток в минуту
- Временная блокировка IP после 10 неудачных попыток
- Captcha после 3–5 попыток

## LIVE-014: Placeholder-функции в production

**Severity:** 🟢 LOW (информационное)
**Страницы:** `/app/settings/profile`, `/app/settings/security`
**Категория:** Product / Completeness

### Описание
В production-версии присутствуют незавершённые функции с плейсхолдерами:

**Профиль:**
- Поле "Телефон" — бейдж "Скоро"
- Поле "Текущая должность" — бейдж "Скоро"
- Поле "О себе" — бейдж "Скоро"

**Безопасность:**
- "Двухфакторная аутентификация" — "Будет доступно в следующем обновлении" + бейдж "Скоро"
- "Активные сессии" — "Управление сессиями будет доступно в следующем обновлении"

### Влияние
- Создаёт впечатление незрелого продукта
- В production рекомендуется скрывать незавершённые функции или использовать waitlist

## LIVE-016: Валидационные ошибки частично на английском

**Severity:** 🟢 LOW
**URL:** API endpoints
**Категория:** Локализация

### Описание
При отправке невалидных данных на API, часть сообщений об ошибках приходит на английском (из Pydantic/FastAPI по умолчанию), в то время как UI полностью русифицирован.

Примеры:
- `"value is not a valid email address"` вместо `"Введите корректный email"`
- `"field required"` вместо `"Обязательное поле"`
