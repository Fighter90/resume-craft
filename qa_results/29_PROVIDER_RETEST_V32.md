## 🔴 KEY-CHECK-001 — ПОДТВЕРЖДЁН КАК P0 BLOCKER

### Описание
Движок оптимизации **не видит сохранённые API-ключи** на новых аккаунтах. При нажатии "Начать оптимизацию" немедленно показывается ошибка "API-ключ не настроен" для КАЖДОГО провайдера, несмотря на то, что все 5 ключей сохранены и отображаются на странице настроек.

### Приоритет: ~~P1 CRITICAL~~ → **P0 BLOCKER**
Повышен до P0, т.к. затрагивает **100% новых пользователей** и **100% провайдеров**. Ни один новый пользователь не может выполнить оптимизацию.

### Результаты тестирования по провайдерам

| # | Провайдер | Модель | Ключ сохранён | Оптимизация | Ошибка |
|---|-----------|--------|---------------|-------------|--------|
| 1 | **GigaChat Pro** | GigaChat-Pro | ✅ MDU2...NA== | ❌ FAIL | "API-ключ для GigaChat не настроен" |
| 2 | **OpenAI** | GPT-4o | ✅ sk-p...QcMA | ❌ FAIL | "API-ключ для OpenAI не настроен" |
| 3 | **Anthropic Claude** | Claude Sonnet 4 | ✅ sk-a...UAAA | ❌ FAIL | "API-ключ для Anthropic Claude не настроен" |
| 4 | **OpenRouter** | AI21: Jamba Large 1.7 | ✅ sk-o...4d2d | ❌ FAIL | "API-ключ для OpenRouter не настроен" |

### Доказательства сохранения ключей

Страница `/app/settings/ai` после перезагрузки показывает:
- ✅ Все 5 провайдеров с зелёной галочкой ✓
- ✅ Каждый ключ отображается как "✓ Сохранён: [маскированный ключ]"
- ✅ Поля ввода показывают "Текущий: [маскированный ключ]"

### Анализ: клиент-сайд ошибка vs сервер

**Ключевое наблюдение:** При нажатии "Начать оптимизацию" redirect на `/app/processing` происходит **мгновенно** с ошибкой — **без сетевого запроса к бэкенду**. Это означает:

1. **Фронтенд проверяет наличие API-ключа в своём внутреннем состоянии (React context/state)** перед отправкой запроса на сервер
2. **Состояние фронтенда не синхронизировано** с данными, сохранёнными на бэкенде
3. Возможные причины:
   - Фронтенд хранит флаг `hasApiKey` в контексте, но не обновляет его после сохранения ключей
   - API endpoint для проверки ключей (`/api/v1/check-key/*`, `/api/v1/providers/*/check`) — **не существует** (возвращает 404)
   - Фронтенд может проверять ключ через отдельный endpoint, который отсутствует на бэкенде
   - Race condition: ключи сохраняются в БД, но кэш фронтенда не инвалидируется

**Дополнительные API-находки:**
- `GET /api/v1/auth/me` — работает, возвращает профиль пользователя (plan: "free", optimizations_used: 0)
- `GET /api/v1/models` — работает, все 5 провайдеров `available: true`
- `GET /api/v1/resumes` — работает, резюме сохранено
- Эндпоинтов для API-ключей (`/api/v1/keys/*`, `/api/v1/api-keys/*`, `/api/v1/providers/keys`) — **нет** (все 404)

### Гипотеза о корневой причине

Наиболее вероятная причина: **фронтенд не получает информацию о сохранённых API-ключах при загрузке страницы оптимизации.**

Сценарий:
1. Пользователь сохраняет ключи на `/app/settings/ai` → ключи записываются в БД ✅
2. Страница настроек показывает ключи (читает из того же state, что и записала) ✅
3. Пользователь переходит на `/app/models` → `/app/processing`
4. Движок оптимизации проверяет наличие ключа через **фронтенд-контекст**, а не через API
5. Контекст **пуст**, потому что данные о ключах не загружаются при навигации между страницами

**Рекомендация:** Добавить API endpoint `GET /api/v1/providers/{provider_id}/has-key` или включить информацию о ключах в ответ `/api/v1/auth/me`. Фронтенд должен проверять наличие ключа через бэкенд, а не через локальное состояние.

## ДОПОЛНИТЕЛЬНЫЕ НАБЛЮДЕНИЯ

### 1. Счётчик оптимизаций — 0/5
Все 5 попыток оптимизации завершились ошибкой "API-ключ не настроен", при этом счётчик `optimizations_used` остался **0**. Это подтверждает, что ошибка происходит **до** обращения к AI-провайдеру — т.е. на этапе клиентской валидации.

### 2. Ошибка в нижнем регистре для Groq
Все провайдеры показывают ошибку с корректным названием ("для GigaChat", "для OpenAI", "для Anthropic Claude", "для OpenRouter"), но для Groq — "для groq" (нижний регистр). Мелкий UI-баг.

### 3. Модель OpenRouter — не самая популярная
Дефолтная модель для OpenRouter — "AI21: Jamba Large 1.7" — не самый популярный/известный вариант. Рекомендуется поставить дефолтом GPT-4o или Claude через OpenRouter.

### 4. Vacancy form — кнопка "Продолжить" disabled
При навигации на страницу вакансии поле "Название должности" показывает placeholder "Product Manager" из резюме, но React state пуст (value = ""). Пользователь должен кликнуть на поле и начать печатать, чтобы кнопка "Продолжить" стала активной. Это может запутать пользователей, которые думают что поле уже заполнено.

## РЕКОМЕНДАЦИИ ДЛЯ ФИКСА

### Приоритет P0 — KEY-CHECK-001 (BLOCKER)

**Вариант 1 (быстрый):** Фронтенд должен проверять наличие ключа через бэкенд API:
```
GET /api/v1/providers/{provider_id}/has-key
Response: { "has_key": true, "provider": "groq" }
```

**Вариант 2 (лучший):** Включить информацию о ключах в endpoint `/api/v1/auth/me`:
```json
{
  "id": "...",
  "email": "...",
  "plan": "free",
  "api_keys": {
    "gigachat": true,
    "openai": true,
    "anthropic": true,
    "openrouter": true,
    "groq": true
  }
}
```

**Вариант 3 (на фронте):** Убрать клиентскую pre-check валидацию. Пусть запрос идёт на бэкенд, и бэкенд сам проверяет наличие ключа и возвращает соответствующую ошибку. Это устраняет рассинхронизацию фронтенда и бэкенда.
