## 🔴 НОВЫЙ ДЕФЕКТ: KEY-CHECK-001 — Оптимизация не видит сохранённые API-ключи (P2 MEDIUM)

**Severity:** P2 (Medium) — блокирует основной функционал оптимизации
**Страница:** /app/processing
**Статус:** NEW — воспроизведён 3 раза
**Аккаунт:** test_qa_v28@example.com

### Описание
При попытке запустить оптимизацию с моделью OpenAI o4-mini, процесс показывает все 4 этапа с зелёными ✓ (Загрузка документа, Анализ вакансии, AI оптимизация, Финализация), но затем выдаёт ошибку:

```
Ошибка обработки
API-ключ не настроен

API-ключ для OpenAI не настроен. Для использования OpenAI необходимо указать
API-ключ в настройках или выбрать другую модель (например, OpenRouter).
```

### Контекст
- API-ключи сохранены и подтверждены через **3 независимых метода**:
  1. **API (PUT):** `PUT /api/v1/settings/ai-keys/openai` → `200 OK, {"has_key": true}`
  2. **API (GET):** `GET /api/v1/settings/ai-keys` → все 5 ключей `has_key: true`
  3. **UI:** Страница /app/settings/ai показывает зелёные ✓ "Сохранён" для всех 5 ключей
- Ошибка воспроизведена **3 раза подряд** на одном аккаунте
- Счётчик оптимизаций **не расходуется** (остаётся 0/5) — провал происходит до фактической оптимизации
- На свежей вкладке (после F5) все провайдеры показывают ✅ зелёные галочки

### API-ключи, подтверждённые на аккаунте

| Провайдер | API Response | UI Status |
|-----------|-------------|-----------|
| GigaChat Pro (Сбер) | ✅ has_key: true | ✅ ✓ Сохранён: MDU2...NA== |
| OpenAI | ✅ has_key: true | ✅ ✓ Сохранён: sk-p...QcMA |
| Anthropic Claude | ✅ has_key: true | ✅ ✓ Сохранён: sk-a...UAAA |
| OpenRouter | ✅ has_key: true | ✅ ✓ Сохранён: sk-o...4d2d |
| Groq | ✅ has_key: true | ✅ ✓ Сохранён: gsk_...GiQv |

### Предполагаемый Root Cause

Бэкенд-процесс оптимизации (/app/processing) проверяет наличие API-ключа **по другому механизму**, нежели API настроек (/api/v1/settings/ai-keys). Возможные варианты:

1. **Проблема кэширования:** Бэкенд оптимизации кэширует состояние ключей и не видит ключи, сохранённые через API (в отличие от ключей, сохранённых ранее через UI на других аккаунтах)
2. **Race condition:** Ключи сохраняются асинхронно, и к моменту проверки при оптимизации бэкенд ещё не видит их
3. **Разные хранилища:** Settings API и Optimization engine читают ключи из разных источников данных
4. **User session привязка:** Ключи привязаны к сессии, а оптимизация проверяет их через другой контекст

### Шаги воспроизведения
1. Создать новый аккаунт
2. Сохранить API-ключ OpenAI через PUT /api/v1/settings/ai-keys/openai
3. Подтвердить сохранение через GET /api/v1/settings/ai-keys → has_key: true
4. Подтвердить в UI → зелёная ✓ "Сохранён"
5. Загрузить резюме
6. Ввести текст вакансии
7. Выбрать OpenAI, модель o4-mini
8. Нажать "Начать оптимизацию"
9. **Результат:** "API-ключ не настроен"

### Рекомендация по исправлению

```python
# Файл: app/services/optimization/engine.py (или аналогичный)

# Убедиться, что проверка ключей использует тот же механизм,
# что и /api/v1/settings/ai-keys

async def check_api_key(user_id: int, provider: str) -> bool:
    # ДОЛЖНО использовать тот же сервис, что и settings API
    key = await ai_keys_service.get_key(user_id, provider)
    return key is not None and len(key) > 0

# НЕ ДОЛЖНО использовать:
# - Кэш, который может быть устаревшим
# - Другую таблицу или хранилище
# - Session-specific данные
```

### Workaround
Не обнаружен. Пользователь НЕ может запустить оптимизацию на новом аккаунте, несмотря на корректно сохранённые ключи.

**ВАЖНО:** Этот баг был обнаружен только на НОВОМ аккаунте (test_qa_v28@example.com). На старых аккаунтах (test@example.com, test_new@example.com) оптимизации работали ранее. Это может указывать на проблему, специфичную для аккаунтов, созданных после определённого обновления, или для ключей, сохранённых через API (а не через UI flow).
