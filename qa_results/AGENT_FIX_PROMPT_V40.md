## 🚨 СИСТЕМНАЯ ПРОБЛЕМА: ПАТТЕРН 503 (ПОДТВЕРЖДЁН V40)

### Описание
Несколько API endpoints возвращают HTTP 503 Service Unavailable, но операции **фактически успешно выполняются** на сервере. Подтверждено стабильно в V39 и V40.

### Затронутые endpoints (V40)

| Endpoint | Метод | HTTP ответ | Реальный результат |
|----------|-------|------------|-------------------|
| /api/v1/auth/me/avatar | DELETE | 503 ❌ | Аватар удалён ✅ |
| /api/v1/auth/me/password | PUT | 503 ❌ | Пароль изменён ✅ |
| /api/v1/auth/logout | POST | 503 ❌ | Сессия завершена ✅ |

### Отдельная регрессия (НЕ часть паттерна 503)

| Endpoint | Метод | V39 | V40 | Операция |
|----------|-------|-----|-----|----------|
| /api/v1/auth/me | DELETE | 200 ✅ | **500 ❌** | Аккаунт **НЕ удалён** |

DELETE /auth/me вернул 500 (не 503!) и операция НЕ выполнилась — это другая проблема, не связанная с паттерном 503.

### Вероятные корневые причины паттерна 503 (в порядке вероятности)

1. **Nginx/Reverse Proxy timeout:** Операция выполняется на backend дольше, чем proxy_read_timeout. Proxy возвращает 503, пока backend продолжает выполнение.
   - **Проверить:** `proxy_read_timeout` и `proxy_send_timeout` в конфигурации Nginx
   - **Решение:** Увеличить таймауты или оптимизировать время ответа

2. **After-response middleware:** Middleware (логирование, аналитика, email-уведомления) после основной операции бросает исключение → 503.
   - **Проверить:** Middleware chain для auth-related endpoints
   - **Решение:** Обернуть after-response hooks в try/catch

3. **Background task error:** Фоновая задача (очистка сессий, уведомления) падает, framework перехватывает исключение.
   - **Проверить:** Celery/background task logs
   - **Решение:** Изолировать фоновые задачи от HTTP response pipeline

### Рекомендованное расследование
```bash
# 1. Проверить серверные логи для 503 ответов
grep "503" /var/log/nginx/error.log
grep "upstream timed out" /var/log/nginx/error.log

# 2. Проверить FastAPI/Uvicorn логи
grep -E "(ERROR|EXCEPTION)" /var/log/app/uvicorn.log

# 3. Проверить middleware chain
grep -r "middleware" app/ --include="*.py"

# 4. Проверить таймауты Nginx
grep -E "(proxy_read_timeout|proxy_send_timeout)" /etc/nginx/

# 5. НОВОЕ V40: Проверить логи для DELETE /auth/me → 500
grep "DELETE.*auth/me" /var/log/app/uvicorn.log | tail -20
```

### ДЕФЕКТ 1 — ACCOUNT-DELETE-500-REGRESSION (P1): Удаление аккаунта → 500 (РЕГРЕССИЯ)

**Проблема:**
Endpoint удаления аккаунта, который работал в V39 (200 OK), теперь возвращает 500 Internal Server Error. Аккаунт НЕ удаляется.

**Шаги воспроизведения:**
1. Перейти на `/app/settings/security`
2. Нажать "Удалить аккаунт" → заполнить пароль + "УДАЛИТЬ" → "Подтвердить"
3. `DELETE /api/v1/auth/me → 500 Internal Server Error`
4. UI: "Внутренняя ошибка сервера"
5. Пользователь остаётся залогинен, все данные на месте

**ВАЖНО:** Это НЕ часть паттерна 503. В паттерне 503 операции выполняются, а ответ неверный. Здесь операция НЕ выполняется — это настоящая серверная ошибка.

**Решение:**
1. Проверить серверные логи для DELETE /api/v1/auth/me
2. Возможные причины: ошибка в миграции БД, новый constraint, изменение в модели User, конфликт с каскадным удалением связанных данных (резюме, вакансии, API ключи)
3. Возможно, недавние изменения в V40 (например, новые таблицы/связи) сломали каскадное удаление

**Серьёзность:** P1 — **РЕГРЕССИЯ.** Ранее работавшая функция сломалась. Блокирует ретест ACCOUNT-DELETE-HARD-vs-SOFT.
