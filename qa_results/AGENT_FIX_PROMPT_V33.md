## 🔴 Замечание 1 (P0 BLOCKER): KEY-CHECK-001 — Движок оптимизации не видит сохранённые API-ключи

### Описание проблемы

При нажатии "Начать оптимизацию" фронтенд **мгновенно** показывает ошибку "API-ключ для [провайдер] не настроен" — без обращения к бэкенду. Ошибка воспроизводится для **ВСЕХ 5 провайдеров** на новом аккаунте.

### Причина (гипотеза на основе анализа)

Фронтенд проверяет наличие API-ключа в своём **локальном React-состоянии** (context/store), а не через бэкенд API. При навигации между страницами состояние не загружается из бэкенда, поэтому фронтенд считает, что ключ не настроен.

**Доказательства:**
1. Ошибка появляется **мгновенно** (без сетевого запроса) — значит проверка клиентская
2. API endpoints для проверки ключей (`/api/v1/check-key/*`, `/api/v1/providers/*/check`, `/api/v1/keys/*`) — **не существуют** (все 404)
3. Страница настроек показывает ключи как сохранённые (читает из бэкенда при загрузке)
4. `GET /api/v1/auth/me` не содержит информации об API-ключах
5. Счётчик `optimizations_used` = 0 — бэкенд даже не вызывался

### Рекомендации по исправлению

**Вариант А (рекомендуемый — бэкенд):**
Добавить информацию о наличии API-ключей в ответ `GET /api/v1/auth/me`:

```python
# В ответе auth/me добавить:
{
    "api_keys_configured": {
        "gigachat": True,
        "openai": True,
        "anthropic": True,
        "openrouter": True,
        "groq": True
    }
}
```

**Вариант Б (фронтенд):**
Добавить API endpoint `GET /api/v1/providers/{provider_id}/has-key` и вызывать его перед оптимизацией:

```typescript
// Перед запуском оптимизации:
const checkKey = await fetch(`/api/v1/providers/${selectedProvider}/has-key`, {
  headers: { Authorization: `Bearer ${token}` }
});
const { has_key } = await checkKey.json();
if (!has_key) {
  showError('API-ключ не настроен');
  return;
}
// Продолжить оптимизацию...
```

**Вариант В (самый быстрый фикс):**
Убрать клиентскую pre-check валидацию полностью. Отправлять запрос на оптимизацию напрямую на бэкенд — пусть бэкенд сам проверяет наличие ключа и возвращает ошибку `400 { "error": "api_key_not_configured" }`.

```typescript
// Вместо клиентской проверки — просто вызвать API
try {
  const result = await optimizeResume(resumeId, provider, model);
} catch (err) {
  if (err.code === 'api_key_not_configured') {
    showError('API-ключ не настроен. Перейдите в настройки.');
  }
}
```

## Замечание 2 (P3): VACANCY-PLACEHOLDER-001 — Placeholder не активирует кнопку "Продолжить"

### Описание

На странице `/app/vacancy` (Ввести вручную) поле "Название должности" показывает placeholder "Product Manager" из загруженного резюме, но React state пуст (`value = ""`). Кнопка "Продолжить" остаётся disabled, пока пользователь не начнёт печатать вручную. Пользователь может подумать что поле уже заполнено.

### Рекомендация

При загрузке страницы вакансии предзаполнять поле "Название должности" реальным значением из резюме (не placeholder), чтобы React state содержал валидное значение:

```typescript
// При инициализации формы:
const defaultTitle = resumeData?.extractedPosition || '';
setVacancyTitle(defaultTitle); // Установить как value, не placeholder
```

## Замечание 3 (P4): GROQ-CASE-001 — Название провайдера в нижнем регистре

### Описание

Ошибка для Groq показывает "API-ключ для groq не настроен" (нижний регистр), в то время как для остальных провайдеров используется корректное написание: "для GigaChat", "для OpenAI", "для Anthropic Claude", "для OpenRouter".

### Рекомендация

Использовать `provider.display_name` вместо `provider.id` в сообщении об ошибке.
