## Замечание 1: KEY-CHECK-001 — РЕГРЕССИЯ: Optimization engine не видит API-ключи

**Приоритет:** P1 CRITICAL 🔴 **БЛОКЕР РЕЛИЗА**
**Компонент:** Backend → Optimization Engine → API key retrieval
**Влияние:** ВСЕ новые пользователи не могут оптимизировать резюме
**Workaround:** Отсутствует

### Описание проблемы

При запуске оптимизации на новом аккаунте (test_qa_v31@example.com) optimization engine не может найти API-ключи, хотя они сохранены и отображаются с зелёным ✓ на странице /app/settings/ai.

Ошибка воспроизведена на 3 из 5 провайдеров:
- **OpenAI (o4-mini):** "API-ключ для OpenAI не настроен"
- **Anthropic Claude (claude-sonnet-4-6):** "API-ключ для Anthropic Claude не настроен"
- **GigaChat Pro:** 400 "Can't decode Authorization header" (другая ошибка, возможно связана)

OpenRouter и Groq не протестированы (Chrome extension disconnect), но по паттерну ожидается тот же результат.

### Важное наблюдение

**Фикс V30 работал для аккаунта test_qa_v30@example.com, но НЕ работает для test_qa_v31@example.com.** Это указывает на то, что фикс V30 мог быть:
1. Привязан к конкретному аккаунту (ручная синхронизация)
2. Зависеть от условий, которые не воспроизводятся для новых аккаунтов
3. Несовместим с изменениями в БД/схеме после V30

### Шаги воспроизведения

1. Зарегистрировать НОВЫЙ аккаунт на https://resumecraft.ru/auth
2. Настройки → AI-модели → сохранить API-ключи для OpenAI, Anthropic и др.
3. Убедиться: все ключи отображают зелёный ✓ Сохранён
4. Мои резюме → загрузить резюме через "Вставить текст"
5. Указать вакансию → "Продолжить"
6. Выбрать OpenAI, модель o4-mini → "Начать оптимизацию"
7. **Результат:** Прогресс-бар показывает 2 зелёных этапа, затем ошибка "API-ключ для OpenAI не настроен"

### Рекомендации по исправлению

```
1. КРИТИЧНО — Проверить, где и как optimization engine получает API-ключи:

   a) Найти функцию/метод, который читает API-ключ при оптимизации:
      - Вероятно в: optimization_service.py, llm_client.py, или подобном
      - Поиск: "api_key", "get_api_key", "api_keys", "not настроен"

   b) Сравнить с тем, где settings page СОХРАНЯЕТ ключи:
      - Вероятно в: settings_service.py, user_settings.py
      - API endpoint: PUT /api/v1/settings/ai или подобный

   c) Убедиться, что оба компонента используют ОДНУ таблицу/коллекцию:
      - SELECT api_key FROM ... WHERE user_id = ? AND provider = ?
      - Сравнить SQL/ORM запросы обоих компонентов

2. Проверить user_id consistency:
   - Settings page сохраняет ключ для user_id X
   - Optimization engine ищет ключ для user_id Y (или другой формат ID)
   - Логировать: print(f"Saving key for user_id={user_id}, provider={provider}")
   - Логировать: print(f"Looking up key for user_id={user_id}, provider={provider}")

3. Проверить возможный кэш:
   - Optimization engine может кэшировать user context при старте
   - Новые ключи не попадают в кэш до рестарта/инвалидации
   - Решение: инвалидировать кэш при сохранении ключей

4. Проверить миграции БД:
   - Сравнить структуру таблицы api_keys/user_settings для V30 vs V31
   - Новые аккаунты могут создаваться с другой версией схемы

5. Диагностический эндпоинт (временный):
   - GET /api/v1/debug/check-keys?user_id=...
   - Вернуть: {provider: has_key, ...} из той же функции, что использует engine
   - Это поможет точно определить, видит ли engine ключи или нет
```

## Замечание 2: HISTORY-RAW-ERROR-001 — Raw ошибки LLM-провайдеров в UI

**Приоритет:** P2 MEDIUM
**Компонент:** Frontend → History page + Processing error page
**Влияние:** Плохой UX — пользователь видит технические детали (URL, HTTP коды, raw JSON)

### Описание проблемы

Ошибки от LLM-провайдеров отображаются как raw technical data на страницах истории и обработки ошибок. Пользователь видит URL-адреса API, HTTP-коды, тела ответов в формате JSON/bytes.

### Примеры ошибок (из V31)

**GigaChat — 400 Authorization Error:**
```
Ошибка: LLM-провайдер gigachat-pro: (URL('https://ngw.devices.sberbank.ru:9443/api/v2/oauth'),
400, b'{"error_description":"Can\'t decode Authorization header","error":"invalid_client"}')
```

**OpenAI o4-mini — max_tokens (из истории V29):**
```
Ошибка: LLM-провайдер openai: Error code: 400 - {'error': {'message':
"Unsupported parameter: 'max_tokens' is not supported with this model.
Use 'max_completion_tokens' instead."
```

### Рекомендации по исправлению

```
1. Создать маппинг ошибок провайдеров → user-friendly сообщений:

   ERROR_MESSAGES = {
       "gigachat": {
           400: "Ошибка авторизации GigaChat — проверьте корректность API-ключа",
           402: "Недостаточно средств на балансе GigaChat — пополните баланс в ЛК Сбер",
           429: "Превышен лимит запросов GigaChat — попробуйте позже",
       },
       "openai": {
           400: "Ошибка параметров запроса к OpenAI — обратитесь в поддержку",
           401: "Неверный API-ключ OpenAI — проверьте ключ в настройках",
           429: "Превышен лимит запросов OpenAI — попробуйте позже",
       },
       "default": "Произошла ошибка при обращении к {provider}. Попробуйте другую модель."
   }

2. Применить маппинг в двух местах:
   a) Backend: в обработчике ошибок optimization engine → возвращать clean message
   b) Frontend: на странице истории → парсить и форматировать ошибку

3. Для страницы истории (/app/history):
   - Если статус = "Ошибка", показывать иконку ⚠️ + короткое сообщение
   - По клику — раскрывающийся блок с деталями (для техподдержки)

4. Для страницы processing error:
   - Уже реализовано для KEY-CHECK-001 ("API-ключ не настроен" + кнопка)
   - Нужно расширить на ВСЕ типы ошибок провайдеров
```

## Замечание 3: FILE-UPLOAD-001 — Загрузка файлов через file input

**Приоритет:** P3 LOW
**Компонент:** Frontend (React) → Upload page
**Workaround:** Вкладка «Вставить текст» работает корректно

### Описание проблемы

При попытке загрузить PDF/DOCX файл через стандартный `<input type="file">` на странице `/app/upload` (вкладка «Загрузить файл»), файл не принимается. Ошибка "Not allowed" на уровне браузерного API.

### Технические детали (из V31 тестирования)

File input элемент:
- `accept=".pdf,.docx"` ✅
- `multiple=false` ✅
- `disabled=false` ✅
- `style.display="none"` — **скрытый** (вызывается через кнопку "Выбрать файл")
- `parentTag="DIV"`

### Рекомендации по исправлению

```
1. Проверить onChange handler для hidden file input:
   - Кнопка "Выбрать файл" должна вызывать fileInput.click()
   - onChange должен получать event.target.files[0]
   - Формировать: new FormData() → append('file', file)

2. Проверить отправку на сервер:
   - POST /api/v1/resumes/upload
   - Content-Type: multipart/form-data (НЕ application/json!)
   - Axios/fetch: НЕ устанавливать Content-Type вручную

3. Проверить CSP headers:
   - Content-Security-Policy не должен блокировать blob: URLs
   - form-action не должен блокировать multipart requests

4. Проверить серверную часть:
   - FastAPI endpoint: async def upload(file: UploadFile)
   - Nginx: client_max_body_size 10M
```

### Тест-кейс для верификации

```
TC-FILE-001: Загрузка PDF через file input
  Шаги:
    1. /app/upload → вкладка «Загрузить файл»
    2. Нажать "Выбрать файл", выбрать PDF (< 5 МБ)
  Ожидание: файл загружен, парсинг, редирект на /app/vacancy

TC-FILE-002: Загрузка DOCX
  Шаги: аналогичные, файл .docx
  Ожидание: аналогичное
```

**Компонент:** Backend → scoring.py

### Рекомендации

Без изменений по сравнению с V30:
```
1. model.eval() перед inference
2. torch.manual_seed(42) перед генерацией эмбеддингов
3. Кэшировать базовый скор по hash(resume_text + vacancy_text)
4. round(score, 1) для нивелирования float precision
```
