## 🚨 СИСТЕМНАЯ ПРОБЛЕМА: ПАТТЕРН 503 (КОРНЕВАЯ ПРИЧИНА)

### Описание
Несколько API endpoints возвращают HTTP 503 Service Unavailable, но операции **фактически успешно выполняются** на сервере. Это системная проблема, а не отдельные баги.

### Затронутые endpoints

| Endpoint | Метод | HTTP ответ | Реальный результат |
|----------|-------|------------|-------------------|
| /api/v1/auth/me/avatar | DELETE | 503 ❌ | Аватар удалён ✅ |
| /api/v1/auth/me/password | PUT | 503 ❌ | Пароль изменён ✅ |
| /api/v1/auth/logout | POST | 503 ❌ | Сессия завершена ✅ |
| /api/v1/auth/me | DELETE | 200 ✅ | Аккаунт удалён ✅ |

### Вероятные корневые причины (в порядке вероятности)

1. **Nginx/Reverse Proxy timeout:** Операция выполняется на backend дольше, чем proxy_read_timeout или proxy_send_timeout. Proxy возвращает 503, пока backend продолжает выполнение.
   - **Проверить:** `proxy_read_timeout` и `proxy_send_timeout` в конфигурации Nginx
   - **Решение:** Увеличить таймауты или оптимизировать время ответа endpoints

2. **After-response middleware:** Middleware (логирование, аналитика, отправка email-уведомлений) выполняется ПОСЛЕ основной операции и бросает исключение, которое трансформируется в 503.
   - **Проверить:** Middleware chain для auth-related endpoints
   - **Решение:** Обернуть after-response hooks в try/catch, чтобы не влияли на HTTP-ответ

3. **Background task error:** Операция запускает фоновую задачу (очистка сессий, отправка уведомлений), которая падает, и framework неверно перехватывает исключение.
   - **Проверить:** Celery/background task logs
   - **Решение:** Изолировать фоновые задачи от HTTP response pipeline

4. **Response serialization error:** Ответ формируется корректно, но при сериализации (Pydantic model, JSON encoder) возникает ошибка на необязательном поле.
   - **Проверить:** Pydantic model для response, наличие Optional полей
   - **Решение:** Добавить default values для всех Optional полей в response models

### Почему DELETE /auth/me возвращает 200
Возможно, endpoint удаления аккаунта не триггерит ту же middleware chain (нет отправки уведомлений, нет обновления сессии), поэтому не попадает под паттерн 503.

### Рекомендованное расследование
```bash
# 1. Проверить серверные логи для 503 ответов
grep "503" /var/log/nginx/error.log
grep "upstream timed out" /var/log/nginx/error.log

# 2. Проверить FastAPI/Uvicorn логи
grep -E "(ERROR|EXCEPTION)" /var/log/app/uvicorn.log

# 3. Проверить middleware chain
grep -r "middleware" app/ --include="*.py"

# 4. Проверить таймауты Nginx
grep -E "(proxy_read_timeout|proxy_send_timeout)" /etc/nginx/
```

### ДЕФЕКТ 1 — PASSWORD-CHANGE-503 (P1): Смена пароля → 503, но пароль реально меняется

**Проблема:**
Эндпоинт смены пароля возвращает 503, при этом пароль фактически меняется на сервере. Frontend обрабатывает 503 как ошибку, что приводит к logout пользователя. При этом logout тоже возвращает 503.

**Шаги воспроизведения:**
1. Перейти на `/app/settings/security`
2. Заполнить: текущий пароль, новый пароль, подтверждение
3. Нажать "Обновить пароль"
4. `PUT /api/v1/auth/me/password → 503 Service Unavailable`
5. Пользователь выброшен на /auth
6. Вход с НОВЫМ паролем → 200 OK (пароль реально сменён)

**Решение:**
1. **Backend/Middleware:** Исправить корневую причину паттерна 503 (см. раздел "СИСТЕМНАЯ ПРОБЛЕМА")
2. **Frontend (workaround):** При 503 на PUT /password — не считать это фатальной ошибкой, показать сообщение "Пароль может быть изменён. Попробуйте войти с новым паролем."

**Серьёзность:** P1 — критичный для пользователя. После смены пароля выбрасывает из аккаунта без объяснения. **НОВЫЙ V39.**

**Решение:** Исправить корневую причину паттерна 503.

### ДЕФЕКТ 4 — ACCOUNT-DELETE-HARD-vs-SOFT (P2): Hard delete вместо soft delete

**Проблема:**
UI текст в "Опасной зоне" обещает soft-delete: "Аккаунт будет помечен для удаления. Через 30 дней все данные будут безвозвратно утрачены. Вы можете отменить удаление в любой момент, просто войдя в аккаунт."

Однако после удаления аккаунт **сразу становится недоступен** для входа (401 Unauthorized). Пользователь не может восстановить аккаунт, как обещает UI.

**Шаги воспроизведения:**
1. Перейти на `/app/settings/security`
2. Нажать "Удалить аккаунт" → заполнить пароль + "УДАЛИТЬ" → "Подтвердить"
3. `DELETE /api/v1/auth/me → 200 OK`
4. Попытка входа с теми же credentials → `POST /api/v1/auth/login → 401`

**Решение (одно из двух):**
- **Вариант А:** Реализовать soft-delete — пометить аккаунт как "pending_deletion", разрешить логин, показать баннер "Ваш аккаунт помечен для удаления, для отмены нажмите кнопку", автоматически удалить через 30 дней
- **Вариант Б:** Обновить UI текст — убрать обещание о восстановлении, предупредить что удаление необратимо

**Серьёзность:** P2 — обман ожиданий пользователя. **НОВЫЙ V39.**
