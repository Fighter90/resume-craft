## 🔴 АКТИВНЫЕ ДЕФЕКТЫ — ТРЕБУЮТ ИСПРАВЛЕНИЯ

### ДЕФЕКТ 1 — AVATAR-DELETE-503 (P2): Удаление аватара → 503

**Проблема:**
На странице `/app/settings/profile` при удалении загруженного аватара сервер возвращает 503 Service Unavailable. UI оптимистично удаляет аватар (silent failure) — пользователь не видит ошибку.

**Шаги воспроизведения:**
1. Перейти на `/app/settings/profile`
2. Загрузить аватар (POST /api/v1/auth/me/avatar → 200 OK)
3. Нажать "Удалить"
4. `DELETE /api/v1/auth/me/avatar → 503 Service Unavailable`

**Текущее поведение UI:**
- Аватар визуально удаляется (оптимистичное обновление)
- Ошибка не показывается пользователю
- При перезагрузке страницы аватар возвращается (т.к. сервер не удалил)

**Решение:**
1. **Backend:** Исправить endpoint `DELETE /api/v1/auth/me/avatar` (503 → 200/204)
2. **Frontend:** Добавить обработку ошибок — показать toast при неудачном удалении
3. **Frontend:** Откатить оптимистичное обновление при ошибке

**Серьёзность:** P2 — backend ошибка, пользователь не может удалить аватар. **Подтверждён V36, V37, V38 (3 версии подряд!).**

### ДЕФЕКТ 2 — GROQ-ALLAM-502 (P2): Groq allam-2-7b → ошибка при оптимизации

**Проблема:**
При оптимизации резюме через провайдер Groq с моделью allam-2-7b процесс завершается ошибкой.

**Шаги воспроизведения:**
1. Загрузить резюме (любой формат)
2. Указать вакансию (любым способом)
3. Выбрать провайдер Groq → модель allam-2-7b
4. Нажать "Начать оптимизацию"
5. POST /api/v1/rewrite → 202 Accepted (OK)
6. GET /api/v1/rewrite/{id}/status → 200 (error status в JSON body)

**V37 поведение:** GET /status → HTTP 502 Bad Gateway напрямую
**V38 поведение:** GET /status → HTTP 200, но с error status в JSON body (изменилась обработка)

**Поведение UI (корректное):**
- Показывает ошибку: "AI-провайдер временно недоступен" ✅
- Счётчик оптимизаций не увеличивается ✅
- Кнопки "Выбрать другую модель" + "Настроить ключи" ✅
- В истории показывает запись с предупреждением ✅

**Решение:**
1. Проверить доступность модели allam-2-7b через Groq API напрямую
2. Если модель нестабильна — добавить fallback на другую модель (llama3-8b, mixtral-8x7b)
3. Улучшить обработку — показать более информативное сообщение (какая именно модель недоступна)
4. Добавить retry logic (1-2 попытки) перед показом ошибки
5. Рассмотреть возможность скрытия/деактивации недоступных моделей в списке выбора

**Серьёзность:** P2 — один из 5 провайдеров полностью неработоспособен с данной моделью. **Подтверждён V37, V38.**

### ДЕФЕКТ 3 — VACANCY-URL-OBJECT-ERROR (P3): UI показывает "[object Object]" при ошибке валидации URL

**Проблема:**
При вводе невалидного URL на вкладке "Вставить URL" страницы вакансии, API корректно возвращает 422, но UI отображает ошибку как "⚠ [object Object]" вместо человекочитаемого сообщения.

**Шаги воспроизведения:**
1. Перейти на `/app/vacancy` → вкладка "Вставить URL"
2. Ввести невалидный URL (например "not-a-valid-url")
3. Нажать "Загрузить"
4. POST /api/v1/vacancies/from-url → **422 Unprocessable Entity** (серверная валидация ✅)
5. UI показывает: **"⚠ [object Object]"**

**Контекст:**
Это регрессия V37 фикса **VACANCY-URL-500**. В V37 была исправлена серверная сторона (500 → 422 + валидация), но frontend код, который ранее обрабатывал текстовую ошибку, теперь получает объект и передаёт его напрямую в отображение.

**Решение:**
1. **Frontend:** В обработчике ошибки `POST /api/v1/vacancies/from-url` извлекать текст из объекта ответа:
   ```javascript
   // Текущий код (предположительно):
   setError(error.response.data); // → "[object Object]"

   // Исправление:
   setError(error.response.data?.message || error.response.data?.detail || 'Ошибка загрузки вакансии');
   ```
2. Добавить типизацию для error response
3. Проверить аналогичные обработчики ошибок в других API-вызовах

**Серьёзность:** P3 — косметический баг, функциональность валидации работает (URL не принимается), но UX страдает из-за нечитаемого сообщения об ошибке. **НОВЫЙ V38.**
