## Замечание 1: FILE-UPLOAD-001 — Загрузка файлов через file input

**Приоритет:** P3 LOW
**Компонент:** Frontend (React) → `UploadPage` / `ResumeUploadForm`
**Workaround:** Вкладка «Вставить текст» работает корректно

### Описание проблемы

При попытке загрузить PDF/DOCX файл через стандартный `<input type="file">` на странице `/app/upload` (вкладка «Загрузить файл»), после выбора файла появляется ошибка:

```
Ошибка: Not allowed
```

Файл не загружается, оптимизация невозможна через файловый ввод.

### Шаги воспроизведения

1. Войти в аккаунт (https://resumecraft.ru/auth)
2. Перейти в «Мои резюме» → нажать «Загрузить резюме»
3. Выбрать вкладку «Загрузить файл»
4. Нажать кнопку выбора файла, выбрать PDF (2-страничное резюме, ~150 КБ)
5. → Ошибка «Not allowed» сразу после выбора файла

### Ожидаемое поведение

Файл загружается на сервер через `POST /api/v1/resumes/upload` (multipart/form-data), парсится, и пользователь перенаправляется на страницу выбора вакансии.

### Возможные причины

1. **CORS / CSP заголовки** — Content-Security-Policy может блокировать form-data запросы или blob URLs
2. **Nginx `client_max_body_size`** — если лимит меньше размера файла (текущий: 10M, маловероятно)
3. **Frontend валидация** — возможно, JavaScript-валидатор блокирует файл до отправки на сервер (MIME-type check, расширение файла)
4. **Rate limiter** — slowapi может перехватывать multipart-запросы как подозрительные
5. **File input event handler** — React SPA может не корректно обрабатывать `onChange` event для file input (missing enctype, missing FormData construction)

### Рекомендации по исправлению

```
1. Проверить browser DevTools → Network:
   - Уходит ли запрос на сервер или ошибка фронтендная?
   - Если 403/415/422 — проблема серверная
   - Если запроса нет — проблема в JS-обработчике

2. Проверить компонент UploadPage:
   - onChange handler для <input type="file">
   - Формирование FormData: new FormData() + append('file', file)
   - Content-Type: должен быть multipart/form-data (не JSON)
   - Axios/fetch config: не должен иметь 'Content-Type': 'application/json'

3. Проверить серверную часть:
   - POST /api/v1/resumes/upload принимает File (fastapi.UploadFile)?
   - CORS allow headers включает multipart?
   - Rate limiter не блокирует upload endpoint?

4. Проверить Nginx:
   - client_max_body_size 10M;
   - proxy_request_buffering on;
```

## Замечание 2: SCORE-VARIANCE-001 — Базовый скор варьируется между запусками

**Приоритет:** P4 INFO
**Компонент:** Backend → `scoring.py` / `calculate_match_score()`
**Влияние:** Косметическое, не влияет на качество оптимизации

### Описание проблемы

При загрузке одного и того же резюме (Senior Software Engineer, Java/Python) и одной и той же вакансии (Senior Java Developer, Яндекс) базовый Match Score (до оптимизации) показывает разные значения:

| Запуск | Базовый скор | Провайдер |
|--------|-------------|-----------|
| 1 | 58 | GigaChat Pro |
| 2 | 56 | OpenAI |
| 3 | 52 | Anthropic Claude |
| 4 | 52 | OpenRouter |
| 5 | 52 | Groq |

Разброс: 52–58 (6 пунктов) для идентичного входного текста.

### Возможные причины

1. **Embedding randomness** — если sentence-transformers используют dropout при inference (маловероятно для eval mode, но стоит проверить `model.eval()`)
2. **Текст парсится неодинаково** — при вставке через текстовое поле могут быть микро-различия в whitespace, encoding, или trim
3. **Кэширование парсинга** — первый запуск парсит заново, последующие могут брать из кэша другую версию
4. **Порядок ключевых слов** — keyword matching может зависеть от порядка, который различается при множественных парсингах
5. **Float precision** — суммирование компонент скора (40% + 25% + 20% + 15%) может давать разные результаты при разном порядке операций
6. **Разные модели = разный pre-score** — если базовый скор вычисляется ПОСЛЕ выбора провайдера и включает LLM-оценку

### Рекомендации по исправлению

```
1. Проверить, вычисляется ли базовый скор до или после выбора LLM-провайдера:
   - Если ДО — скор должен быть детерминированным
   - Если ПОСЛЕ — LLM может влиять на оценку

2. В calculate_match_score() / calculate_match_score_detailed():
   - Убедиться, что model.eval() вызывается перед inference
   - Зафиксировать seed: torch.manual_seed(42) перед генерацией эмбеддингов
   - Использовать round(score, 1) для нивелирования float precision

3. Кэширование:
   - Кэшировать базовый скор по hash(resume_text + vacancy_text)
   - При повторном запросе с тем же входом — возвращать тот же скор

4. Логирование:
   - Добавить debug-лог: parsed_text hash, embedding dimensions, sub-scores
   - Это поможет точно определить источник вариации
```

### Тест-кейс для верификации

```
TC-SCORE-001: Детерминированность базового скора
  Предусловие: аккаунт с подпиской, одно и то же резюме и вакансия
  Шаги:
    1. Загрузить резюме (вставка текста)
    2. Указать одну и ту же вакансию
    3. Выбрать GigaChat Pro → записать базовый скор
    4. Повторить шаги 1-3 ещё 2 раза
  Ожидание: базовый скор идентичен во всех 3 запусках (±1 пункт допустимо)
```
